# Karpathy 영감 Claude Code 가이드라인 (개선판)

[English](README.md) | 한글

[Andrej Karpathy의 LLM 코딩 함정 관찰](https://x.com/karpathy/status/2015883857489522876)에서 출발해, Claude Code의 동작을 개선하기 위한 강화된 `CLAUDE.md`입니다.

이 README는 세 단계로 구성됩니다:

1. **Karpathy가 지적한 문제들**
2. **[forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills)** 가 4개 원칙으로 이를 어떻게 풀었는지
3. **이 fork의 추가 개선** — 패턴 기반 트리거, 새 원칙 두 개, 그리고 군더더기 제거

## 문제들 (The Problems)

Andrej의 포스트 인용:

> "모델은 사용자를 대신해 잘못된 가정을 만들고, 확인 없이 그대로 진행한다. 자신의 혼란을 관리하지 않고, 명확화를 구하지 않으며, 불일치를 표면화하지 않고, 트레이드오프를 제시하지 않으며, 필요할 때 반대 의견을 내지도 않는다."

> "여전히 약간 비위 맞추는(sycophantic) 경향이 있다."

> "코드와 API를 과하게 복잡하게 만들고, 추상화를 비대화시키고, 죽은 코드를 정리하지 않고… 100줄이면 될 일을 1000줄짜리 비대한 구조로 구현한다."

> "여전히 작업과 무관함에도 자신이 충분히 이해하지 못한 코드와 주석을 부수 효과로 변경하거나 제거한다."

> "에이전트가 무언가를 끈질기게 붙들고 있는 모습을 보는 건 흥미롭다. 지치지 않고, 의기소침해지지도 않고, 그냥 계속 시도한다…"

다섯 가지 실패 양상으로 정리할 수 있습니다: **묵시적 가정**, **비위 맞추기**, **비대화**, **부수 효과 편집**, **맹목적 끈기**.

## forrestchang의 CLAUDE.md는 이 문제들을 어떻게 다뤘는가

upstream은 응답을 **4개 원칙**으로 구성하고, 각각이 Karpathy의 문제 중 하나 이상에 대응합니다:

| upstream 원칙 | 대응하는 Karpathy 문제 |
| --- | --- |
| **§1 Think Before Coding** | 잘못된 가정, 숨겨진 혼란, 트레이드오프 누락, 명시되지 않은 push-back |
| **§2 Simplicity First** | 과복잡화, 비대한 추상화, 1000줄짜리 구조 |
| **§3 Surgical Changes** | 인접 코드에 대한 부수 효과 편집, 죽은 코드 생성 |
| **§4 Goal-Driven Execution** | Karpathy의 "성공 기준에 맞춰 루프를 돌려라" 통찰을 활용 (테스트 우선, 선언적 목표) |

upstream 버전은 **자기 인식 트리거**를 사용합니다 — 예: *"확실하지 않으면 물어봐라"*, *"여러 해석이 가능하면 제시하라"* — 그리고 마지막에 자가 점검을 덧붙입니다 (*"시니어 엔지니어가 보면 과복잡하다고 할까?"*, *"200줄을 50줄로 줄일 수 있으면 다시 작성하라"*).

upstream이 **직접 다루지 않은** 것들:

- **비위 맞추기 (Sycophancy)** — *"필요할 때 반대 의견을 내라"* 한 줄로 §1 안에 묻혀 있어 놓치기 쉬움
- **코드베이스와 요청 간의 불일치** — 명시되지 않음
- **코드와 그 자체 주석의 불일치** — 명시되지 않음
- **맹목적 끈기 (Blind tenacity)** — Karpathy의 끈기 관찰 (*"그냥 계속 시도한다…"*)에 대응하는 규칙이 없음. 모델이 멈추고 에스컬레이션할 시점에 대한 지시가 전무함

## 이 fork가 추가로 개선한 점

upstream 위에 다섯 개의 집중된 변경, 그리고 모든 원칙을 떠받치는 `Foundations` 블록입니다.

| 변경 | 이유 |
| --- | --- |
| **상단 Foundations 섹션** | 번호 매겨진 원칙들 위에 두 개의 비협상 항목을 명시: *침묵하며 결정하지 말 것*, *사소한 일은 판단으로 처리하고 강한 성공 기준에서는 자율적으로 루프 돌릴 것*. 다섯 원칙 전체를 떠받치는 앵커 역할. |
| **패턴 기반 트리거** | *"확실하지 않으면 물어봐라"* 는 LLM이 신뢰성 있게 갖추지 못한 자기 인식에 의존함. 외부에서 검증 가능한 조건으로 교체: *사용자가 이걸 명시했나?*, *변경이 위험한가 (아키텍처/의존성/스키마/넓은 범위)?*, *입력들이 서로 모순되나?* |
| **트레이드오프 축 명명** | 모호한 *"트레이드오프를 표면화하라"* → 네 개의 명시적 축: **scope, time, quality, reversibility**. "무엇이 트레이드오프인지" 모호성을 줄임. |
| **push-back 규칙 명시화 + 경계 설정** | upstream의 한 줄 *"Push back when warranted"* → *"사용자 접근에 결함이 있으면 → **한 번** push back, 그 후 따른다"*. 의도는 같지만 경계를 둬서 잔소리로 변하지 않도록 함. 비위 맞추기 문제 직접 대응. |
| **§1에 불일치 규칙 추가** | *"코드베이스가 요청과 모순되거나, 코드가 자체 주석과 모순되면 → 행동 전 질문"*. upstream에는 없음. |
| **§3에 주석 보존 규칙 추가** | *"작업이 요구하지 않는 한, 기존 주석을 편집/재작성/제거하지 말라"*. Karpathy의 *"여전히 주석을 변경하거나 제거한다…"* 관찰에 대한 직접 대응. upstream에는 없음. |
| **§5 Know When to Stop (신규)** | Karpathy의 끈기 관찰은 양날의 검. 3회 실패 임계값 + 구조화된 에스컬레이션 양식으로 맹목적 재시도를 체크포인트로 변환. |
| **자가 점검 의식 제거** | *"시니어 엔지니어가 과복잡하다고 할까?"*, *"200줄 → 50줄 재작성"* 같은 항목 제거. LLM은 사후 자기성찰이 아니라 생성 중에 규칙을 적용하므로, 이런 줄들은 토큰만 소비하고 실제 행동을 바꾸지 못함. |

> ⚠️ **트레이드오프: 토큰 비용** — 이 추가들은 `CLAUDE.md`를 **~590 토큰 (±20)** (upstream, 2,357 chars / 358 words)에서 **~690 토큰 (±20)** (이 fork, 2,754 chars / 418 words)으로 늘립니다 — 약 **+17%**. 절대 토큰 수는 추정값입니다 (4 chars/token + BPE word ratio ~1.3 tokens/word 교차 검증). 다만 **+17% 증가율 자체는 추정 방식과 무관하게 안정적**이므로, 신뢰할 수 있는 수치는 비율 쪽입니다. 정확한 값이 필요하면 Anthropic SDK의 `client.messages.count_tokens()` 를 사용하세요. 모든 대화가 시스템 프롬프트에서 이 비용을 지불하므로, 추가된 원칙들은 그 오버헤드를 정당화할 만큼 실수를 예방해야 net win입니다.

### +17%는 그만한 가치가 있나? — 중립적 평가

질문에 솔직하게 답할 가치가 있습니다. **upstream과의 정량 비교는 없습니다** — 각 규칙이 Karpathy의 어떤 문제에 가장 직접적으로 대응하는지에 기반한 구조적 논거일 뿐입니다. 두 버전을 비교하는 벤치마크는 존재하지 않습니다.

**비용을 정당화할 가능성이 높은 항목:**

- **§5 Know When to Stop** — Karpathy의 끈기 관찰에 직접 대응. 30분 헛돌림 루프 한 번만 방지해도 +100 토큰을 여러 번 회수. upstream에는 동일 규칙 없음.
- **§3 주석 보존** — *"이해 못한 코드와 주석을 변경"* 관찰에 직접 대응. 세션당 한 번이라도 drive-by 주석 편집을 막으면 plausibly net positive.
- **§1 불일치 규칙** — *코드베이스가 요청과 모순* 은 흔한 실패 양상이며 upstream은 명시적으로 다루지 않음. 한 번이라도 잡으면 침묵의 breakage 한 부류 예방.

**더 사변적인 항목 (그럴듯하지만 입증되지 않음):**

- **Foundations 섹션** — §1과 부분적으로 중복. anchor 역할이지만 동일 내용이 아래 확장된 형태로 존재.
- **명명된 트레이드오프 축** — *scope/time/quality/reversibility* 는 upstream의 모호한 *"surface tradeoffs"* 보다 구체적이지만, 명시화가 실제로 모델 행동을 바꾸는지는 테스트되지 않음.
- **패턴 기반 트리거** — 이론적 논거 (외부 조건이 자기 성찰보다 일관되게 적용된다)는 합리적이지만 측정 안 됨.
- **경계 있는 push-back** — *"한 번, 그 후 따른다"* 는 합리적 경계지만, upstream의 한 줄 *"Push back when warranted"* 가 실무에서는 같은 영역을 이미 커버할 수도 있음.

**솔직한 요약:** 모델이 도무지 풀리지 않는 접근에 시간을 태우거나 인접 코드를 조용히 망가뜨리는 일을 자주 본다면, **§5 + 주석 보존만으로도 +100 토큰은 정당화** — 이 두 규칙이 실용 가치의 대부분을 짊어집니다. 나머지 변경들은 upstream보다 *구조적으로 더 탄탄*하지만 입증된 우월성은 아닙니다. 그런 실패 양상을 잘 만나지 않는다면, upstream의 4-principle 버전이 충분하고 더 저렴할 가능성이 높습니다.

솔직한 표현: **이 fork는 가설 기반 리파인먼트이지, 측정된 개선이 아닙니다.**

## 다섯 원칙 (The Five Principles)

### Foundations

- **Core:** 침묵하며 결정하지 말 것 — 행동 전에 묻거나, 응답에 가정을 표면화하라.
- **Autonomy:** 사소한 일은 판단으로 처리하라 (보고서에 그 결정을 명시). 성공 기준이 강하면 자율적으로 루프를 돌려라.

### 1. Think Before Coding

가정하지 말 것. 혼란을 숨기지 말 것. 다음 상황에서 사용자에게 표면화할 것:

- **위험** (아키텍처, 의존성, 스키마, 넓은 범위) → 먼저 물어볼 것; 그 외에는 "X를 가정함 — 아니면 알려주세요"
- **트레이드오프 축에 해당** (scope, time, quality, reversibility) → 명명하고 사용자가 선택하게 할 것
- **사용자 접근에 결함** → 한 번 push back, 그 후 따른다
- **불일치** (코드베이스 vs 요청, 코드 vs 주석) → 행동 전 질문

### 2. Simplicity First

문제를 푸는 최소 코드. 추측성 코드는 없음.

- 요청되지 않은 기능 추가 금지.
- 일회성 코드를 위한 추상화 금지.
- 요청되지 않은 "유연성"이나 "구성 가능성" 금지.
- 발생할 수 없는 시나리오에 대한 에러 처리 금지.

### 3. Surgical Changes

반드시 손대야 하는 것만 손댈 것 — 변경된 모든 줄은 사용자 요청으로 추적되어야 함; 그렇지 않으면 되돌릴 것. 본인이라면 다르게 할지라도 기존 스타일에 맞출 것. 작업 외 부분의 리팩터링/포맷팅/이름 변경/주석 재작성 금지. *본인의* 변경이 만든 미사용 import/변수/함수만 제거할 것. 무관한 이슈(기존 죽은 코드 등)는 응답 끝에 보고할 것 — 조용히 고치지 말 것.

### 4. Goal-Driven Execution

성공 기준을 정의할 것. 검증될 때까지 루프 돌릴 것. 모호한 작업을 검증 가능한 목표로 변환 — 보통 테스트 우선:

- "검증 추가" → "잘못된 입력에 대한 테스트를 작성하고, 통과시켜라"
- "버그 수정" → "버그를 재현하는 테스트를 작성하고, 통과시켜라"
- "X 리팩터링" → "리팩터링 전후로 테스트가 모두 통과하는지 확인하라"

다단계 또는 다중 결정 요청에는, 단계별 검증을 포함한 계획을 먼저 제안할 것.

### 5. Know When to Stop

끈기는 강점. 맹목적 끈기는 낭비.

- 3회 시도 실패 후(또는 미세한 변형으로 침묵 재시도 후), 멈추고 실패를 요약, 방향을 물어볼 것.
- 수정이 새 실패를 연쇄적으로 유발하면, 한 발 물러나 접근을 재고할 것 — 패치를 계속하지 말 것.

에스컬레이션 양식이 이를 구체화함: 시도한 각 항목, 실패 이유, 그리고 추정 가능한 진로 — 그 후 대기.

## 설계 결정 (Design Decisions)

### 자기 인식이 아닌 패턴 기반 트리거

LLM은 자신의 불확실성을 신뢰성 있게 인식하지 못합니다. *"확실하지 않으면 물어봐라"* 는 *"자신감을 느끼면, 침묵하며 진행하라"* 로 무너지는 경향이 있습니다. 이 버전은 자기 성찰을 **외부에서 검증 가능한 조건**으로 교체합니다 — *사용자가 명시했나?*, *아키텍처/스키마/의존성을 건드리나?*, *입력들이 서로 모순되나?* 생성 중에 일관되게 적용하기 더 쉽습니다.

### 독립 sycophancy 규칙 대신 경계 있는 push-back

결함 있는 접근에 push-back 하는 것은 *"혼란을 숨기지 말라"* 의 특수 케이스입니다 — 결함 *자체*가 표면화해야 할 혼란이기 때문입니다. 이를 독립 원칙이 아닌 §1 sub-bullet으로 두고 *"한 번, 그 후 따른다"* 는 경계를 추가하면, 침묵의 순응이나 반복적 잔소리 어느 쪽으로도 무너지지 않습니다.

### §5가 존재하는 이유

Karpathy: *"지치지 않고, 의기소침해지지도 않고, 그냥 계속 시도한다…"* 그 끈기는 진정한 레버리지지만, 동시에 도무지 풀리지 않는 접근에 30분 침묵 재시도를 만들어 냅니다. 3회 임계값과 구조화된 에스컬레이션 양식이 그 에너지를 슬롯머신이 아닌 체크포인트로 바꿉니다.

## 설치 (Install)

**옵션 A: CLAUDE.md (권장)**

새 프로젝트:

```bash
curl -o CLAUDE.md https://raw.githubusercontent.com/nyjin/andrej-karpathy-skills/main/CLAUDE.md
```

기존 프로젝트 (덧붙이기):

```bash
echo "" >> CLAUDE.md
curl https://raw.githubusercontent.com/nyjin/andrej-karpathy-skills/main/CLAUDE.md >> CLAUDE.md
```

**옵션 B: Skills 디렉토리**

```bash
mkdir -p skills/karpathy-guidelines
curl -o skills/karpathy-guidelines/SKILL.md https://raw.githubusercontent.com/nyjin/andrej-karpathy-skills/main/skills/karpathy-guidelines/SKILL.md
```

## 잘 작동하고 있는지 확인하는 법

- 다이프에 불필요한 변경이 줄어듦
- 과복잡화로 인한 재작성이 줄어듦
- 명확화 질문이 실수 이후가 아닌 구현 이전에 들어옴
- 침묵의 순응 대신 push-back과 트레이드오프 분석
- 20분 헛돌림 후가 아니라 일찍 실패가 보고됨

## 변경 이력 (Changelog)

upstream [forrestchang/andrej-karpathy-skills](https://github.com/forrestchang/andrej-karpathy-skills) 대비 변경:

- **Foundations** 섹션 추가 — 원칙들 위에 명시적 Core + Autonomy 규칙
- **§5 Know When to Stop** 추가 — 3회 시도 임계값 + 에스컬레이션 양식
- **불일치 처리** §1에 추가 — 코드베이스 vs 요청, 코드 vs 주석
- **명명된 트레이드오프 축** 추가 — scope, time, quality, reversibility
- **주석 보존 규칙** §3에 추가 — 작업 외 기존 주석 편집/재작성/제거 금지
- **push-back 규칙 명시화 + 경계** §1에 — 한 번, 그 후 따른다
- **트리거를 자기 인식에서 패턴 기반으로 전환** — 외부 검증 가능 조건
- **자가 점검 의식 제거** (*"시니어 엔지니어 과복잡?"*, *"200줄 → 50줄"*) — 측정 가능한 행동 효과 없음
